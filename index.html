Nubra · AI Product Plan

Nubra AI Trading Mode

An end-to-end system that takes a trader from an idea to a strategy running on Nubra Cloud, without writing code.

Four modules on one shared engine: Chart Analytics AI, Strategy Coder, One-click Deployment and Strategy Recorder, built on a Backtest Engine.

Target state, requirements and phased delivery plan · Engineering review · November 2026
Target state

Target architecture: multiple entry points, one Strategy Creator, one deployment path

Each entry point yields a strategy specification. The Strategy Creator converts it into Nubra Python SDK code. The same code is backtested, then deployed with one click.

Foundations

Foundations required for the target state

One strategy representation

Every entry point ends in the same thing: a plan (data, numbers, rules with the sentence each came from, assumptions, questions). The Coder, the backtest and the deploy all read it. Nothing is special-cased per entry point.

One target: the Nubra Python Cloud SDK

Generated code is always main.py + .env + requirements.txt on SDK 0.5.4, PROD, API-key login. The same files run in the backtest and on the Cloud.

Market history, served to us

Candles, L1 bid/ask, OI, option chains and greeks, by instrument and date, without a user's credentials. Needed by the backtest, by Chart AI's levels and option-chain analysis, and by the morning check.

Cloud contracts

Auto-save of a created strategy, start on click, .env installed into the VM, a defined behaviour when a running strategy is overwritten.

Model outputs verified by code and review

Plan writer, code writer, description writer, decision step, Chart AI analysis. Each is followed by plain-code checks, and every delivery is reviewed by a stronger model after the fact. Fixes solve a class of error, not one case.

User context and storage

Texts, answers, plans, files, chart results and the user's chart setup, kept until the user deletes them. Chart AI's morning check and the Recorder both depend on remembered context.

Target capability: chart analysis with a trader's judgement

Reads the chart

  • Quick analysis with entry, exit and S&R levels
  • S&R drawn by AI from previous-day data, OI and the option chain
  • An AI view of the market from many parameters, as a sceptic against the user's own view
  • Option-chain analysis on the chart itself, to spot momentum
  • Setups and signals across time frames, from many indicators
  • Indicators (117 standard TradingView ones) and divergence analysis

Acts on the chart

  • Drawings with a trader's skill: Fibonacci, trend lines, and what a trader does with each
  • Charting-setup automation: the user's routine actions turned into a Pine-based custom indicator

Knows the user's setup

  • Morning check: are the lines drawn as per the user's setup, what is off, where entry and exit are
  • Current positions: an AI view with OI and option-chain data, and an alert when a position has flaws

Surface and hand-off

  • All abilities shown as nudges on the same interface
  • A setup the AI has read can be handed to the Strategy Coder as text: "make this a strategy"

Bridge to AI mode for non-chart requests

  • A question that is not about the chart (end-of-day positions review, stock screening by volume, account-level questions) is not refused
  • Chart AI passes the prompt to AI mode and shows AI mode's answer in the same interface

Module 2 · Strategy Coder

Target capability: strategy text to verified Nubra SDK code

What the user gets, together

  • main.py: 12 modules; only data, calculations and conditions are written per strategy, the rest is a fixed tested template
  • .env: every changeable value (instruments, size, times, periods, limits), each with the sentence it came from; assumptions marked ASSUMED
  • requirements.txt: nubra-sdk 0.5.4, pandas, numpy
  • A description derived from the code, assumptions highlighted
  • A chart of the orders the rules would have placed in the last 7 trading days, each with the sentence that fired

Clarification policy

Safe gaps are assumed (size, interval, standard indicator periods) and editable in .env. Unsafe gaps (instrument, direction, exit, contradictions) are asked: one question per round, all remaining in round 3, then one build. The number of rounds is bounded.

How it works

  • Plan writer (model) → plan checks (plain code, about 110 rules) → up to 3 attempts
  • Data writer (plain code) writes module 1, .env, requirements.txt
  • Code writer (model) writes calculations and conditions → static checks → up to 2 fixes
  • Description writer and replay run in parallel; all delivered at once
  • Feedback: a decision step picks ENV (edit .env), LOGIC (regenerate changed rules only) or REDO

What it needs

  • Instrument service (names, expiries, contract picker, BSE, MCX)
  • Market history for the replay, without user credentials
  • Storage of every request; a learning loop that reviews 100% of deliveries weekly
  • Targets: 95% pass on the 600-text suite, 10 minutes to delivery, 2% or fewer not built

Module 3 · One-click Deployment

Target capability: deployment to Nubra Cloud in one action

What the user sees

  • A Deploy button next to the code, description and chart: saves the strategy on Nubra Cloud and starts it under the Cloud's schedule
  • An Edit code button: opens the saved strategy on the Cloud script screen
  • An .env form in the product: change instrument, size, times; the chart reruns before deploying
  • Feedback in words: a summary of the change, confirm, then the saved strategy is overwritten

Responsibilities retained by Nubra Cloud

Running, monitoring, stopping, the run calendar and holidays. The product never reads a user's API key, phone, OTP or MPIN; login is always PROD with API-key login inside the generated code.

What it needs from the Cloud team

  • Auto-save of every created strategy (an API, not a click)
  • Start a saved strategy on click
  • .env installed into the strategy's VM (confirmed)
  • Defined behaviour when a running strategy is overwritten
  • SDK 0.5.4 on the Cloud (confirmed)

What it needs from us

  • Exactly three files, a strategy tag per order, rate limits respected in the template
  • The .env form and change summary in the frontend
  • A version stamp on every delivery, so a description always says which version it describes

Module 4 · Strategy Recorder

Target capability: strategy text derived from recorded trading

User flow

The user enables recording and trades on the Nubra interface as usual: draws levels, adds indicators, places and exits orders. The user then stops the recording.

Recorder function

  • Captures the events, not pixels: orders with time and price, drawings, indicator changes, the chart state when each order was placed
  • Turns the events into strategy text in the user's own terms: "bought when price closed above the trend line with RSI below 40"
  • Shows the text; the user corrects it; the text goes to the Strategy Coder like any typed text

Scope: an entry point to the Strategy Coder

From the text onward the flow is identical: same plan, same questions, same code, same chart, same deploy. The Recorder's only job is to produce good text.

What it needs

  • An event schema: which UI events, with what fields, and consent to record
  • Event capture in the trading UI (frontend)
  • An events-to-text model step with its own checks
  • A test set of recorded sessions with the strategy the trader meant (T-REC30)
  • The Coder's text entry point, as is

Open questions

  • Discretionary trades: what to do when the events show no consistent rule
  • How many sessions make one strategy
  • Whether Chart AI's drawing data is the same event stream

Shared engine · Backtest

Target capability: historical execution of the delivered code before deployment

What it does

  • Runs the delivered main.py unchanged against a stand-in market fed with real history: candles, L1, OI, option chains, greeks
  • Shows orders on the chart, each with the sentence of the text that fired, and ASSUMED where an assumption decided
  • Trade list, P&L after fees and slippage, drawdown; a results screen with Deploy on it
  • Read-only: no user key, no order to the exchange, isolated with time and memory limits

What exists

A 7-trading-day replay on real PROD candles with a stand-in SDK, option replay with OI and greeks, and a marks file the chart reads. It is a lab tool with a paste-and-run page.

Phases

  • Phase 1 · we are here: 7-trading-day replay, lab tool
  • Phase 2: delivered with every strategy from the Coder; 'no orders' and 'not replayable' states; fixed window
  • Phase 3: full history, user-chosen window, P&L with fees and slippage, option strategies with greeks and OI, limits for partial-history cases
  • Phase 4: results screen with Deploy; compare versions; the backtest replaces the 7-day chart

What it needs

  • History supply without user credentials (backend decides)
  • Time and memory limits for the isolated process
  • A fill model that states its limits: 1-minute candles, no order depth
  • A decision: ship the stand-in SDK or write a smaller replay-only market

Decisions required and next steps

Decisions
